### R1: Dataset reuse strategy (FR-028, FR-029, Edge Case #2)

**Decision**: The notebook reads the 2025 Stack Overflow Annual Developer Survey CSV from the L11 location, `lectures/11-pandas-analytics/data/survey_results_public.csv`. A single `SURVEY_CSV_PATH` constant holds the path. If the file does not exist, the notebook prints a loud message ("Survey CSV not found at <path>; using synthetic data instead — see lectures/11-pandas-analytics/README.md to enable the real dataset") and falls back to a synthetic 4-feature, 2-class dataset generated by `np.random.default_rng(seed=42)`.

**Rationale**: Re-downloading or duplicating the CSV would (a) waste student disk space, (b) drift the two lectures' schemas over time, and (c) violate the "no embedded dataset" precedent set by L11. Pointing at the L11 path keeps both lectures synchronized and lets the instructor demo on either path. The synthetic fallback satisfies FR-029 and Edge Case #2 (notebook MUST run end-to-end without the CSV) without introducing a new download story.

**Alternatives considered**:
- Auto-download from `survey.stackoverflow.co` on first cell — violates FR-031 (no network calls) and breaks in offline-classroom scenarios.
- Bundle a tiny CSV sample in the L12 directory — violates the L11 precedent (no committed dataset) and creates a divergent schema risk.
- Skip the Survey entirely and use only synthetic data — loses the "real-world data motivates ML" pedagogical hook and breaks the L11 → L12 narrative arc.

### R2: Binary classification target (FR-015)

**Decision**: The binary target is **"above-median `ConvertedCompYearly` within the respondent's country"**. For each Survey row:

1. Drop rows with missing `Country` or missing `ConvertedCompYearly`.
2. Compute the median compensation **per country** via `df.groupby("Country")["ConvertedCompYearly"].transform("median")`.
3. Set `y = (df["ConvertedCompYearly"] > country_median).astype(int)`.

The result is a balanced binary target by construction (≈ 50/50 within each country, modulo ties). Globally, the imbalance is mild and learnable.

**Rationale**: A naive "above global median" target is dominated by a single feature ("respondent lives in the US/Switzerland/etc.") and the classifier learns nothing interesting beyond country one-hots. Per-country median elevates within-country signals — work experience, education, remote work — which is exactly what the four-feature model can plausibly learn. It also keeps the example *non-sensitive* (we are not predicting an individual's salary, just whether they are above or below their own country's median, and the notebook will say so plainly).

**Alternatives considered**:
- Above-global-median compensation — trivially predicted by country, defeats the lesson.
- "Identifies as professional developer" (`MainBranch`) — too easy; converges in 50 epochs and doesn't motivate gradient descent.
- "Wants to learn Rust next year" (multi-value target derived from `LanguageWantToWorkWith`) — interesting but requires `.explode()` reshaping that re-teaches L11 content.
- Synthetic-only targets — loses the real-data motivation.

**Decision**: Four features for the lecture body, with a fifth optional feature reserved for mini-project Part 3 homework:

After `dropna` on rows missing any of features 1–3 OR the target, expected `X.shape ≈ (28000–32000, 4)` and `y.shape ≈ (28000–32000,)` on the 2025 Survey. Both well within the 90-second / 1000-epoch budget on a typical laptop.

**Rationale**: Four features keep the example concrete and visualizable on a slide. Mixing two raw numeric (`years_code`, `work_exp`), one ordinal (`ed_level_ord`), and one binary (`is_remote`) gives students a realistic "you'll have to encode things" experience without needing one-hot encoding (deferred to the homework). **Alternatives considered**:
- Use `Age` raw — the 2025 Survey ships `Age` as a bucketed string ("18-24", "25-34", ...), not raw years; would require extra parsing that distracts from ML.
- One-hot `DevType` directly in the lecture — bumps feature count to 20+ and makes the gradient descent harder to visualize; pushed to homework instead.
- Drop `is_remote` and use only 3 numeric features — loses the "categorical-as-numeric" teaching opportunity.

### R4: Synthetic-fallback dataset shape (FR-029)

**Decision**: When the Survey CSV is missing, generate a synthetic dataset with `np.random.default_rng(seed=42)` matching the lecture's expected shape:

```python
N_SYNTH = 5000
P_SYNTH = 4
rng = np.random.default_rng(seed=42)
X_synth = rng.standard_normal((N_SYNTH, P_SYNTH))
true_w = np.array([1.5, -1.0, 0.8, 0.3])
true_b = -0.5
logits = X_synth @ true_w + true_b
probs = 1.0 / (1.0 + np.exp(-logits))
y_synth = (rng.uniform(size=N_SYNTH) < probs).astype(int)
```

Synthetic features have the same shape `(n, 4)` as the Survey path, so all downstream cells (standardize / split / train / eval / save / load) execute identically. Expected synthetic accuracy at convergence: ≈ 0.80.

**Rationale**: Keeping the same `(n, 4)` shape between the real and synthetic paths means the rest of the notebook is path-agnostic — only the loading cell branches. The synthetic data is generated *with a known true `w` and `b`*, so we can also (optionally, in a hidden cell) compare the recovered weights to the ground truth as a "did the math work?" sanity check.

**Alternatives considered**:
- `sklearn.datasets.make_classification` — adds the exact dependency we are trying to avoid having as a runtime requirement.
- Iris dataset — ships with sklearn; adds the same dependency. Also is multi-class (3 classes), wrong for binary logistic regression.
- Hand-built 2D toy dataset — too small to demonstrate gradient-descent dynamics meaningfully.

### R5: Numerically stable sigmoid (FR-018, Edge Case #6)

**Decision**: Implement sigmoid via the standard branch-on-sign trick to prevent `np.exp` overflow on large negative `z`:

```python
def sigmoid(z):
    """Numerically stable sigmoid. Avoids overflow for large negative z."""
    pos = z >= 0
    out = np.empty_like(z, dtype=np.float64)
    # For z >= 0: 1 / (1 + exp(-z)) — exp(-z) is in (0, 1], no overflow
    out[pos] = 1.0 / (1.0 + np.exp(-z[pos]))
    # For z <  0: exp(z) / (1 + exp(z)) — exp(z) is in (0, 1), no overflow
    exp_z = np.exp(z[~pos])
    out[~pos] = exp_z / (1.0 + exp_z)
    return out
```

A short comment in the cell explains *why* the naive `1 / (1 + np.exp(-z))` overflows when `z` is very negative (e.g., `np.exp(1000)` → `inf`).

**Rationale**: The branch-on-sign trick is the same one `scipy.special.expit` uses internally (verified by reading scipy source). It needs only NumPy (no scipy dep) and is exactly two short branches — small enough to fit in one teaching cell. Showing it next to the naive version gives students a real-world example of "numerical stability" that they will encounter again in any future ML course.

**Alternatives considered**:
- `np.where(z >= 0, 1.0 / (1.0 + np.exp(-z)), np.exp(z) / (1.0 + np.exp(z)))` — concise but evaluates BOTH branches, so `np.exp(-z)` still overflows on large negative z and emits a runtime warning even though the value is masked away. Worse pedagogically because it's silently wrong.
- Use `scipy.special.expit` — adds a scipy dependency; we are intentionally NumPy-only.
- Clip z to `[-500, 500]` before computing — works but obscures the underlying problem and the elegance of the fix.

### R6: Loss function and gradient — analytic vs autodiff (FR-018, FR-019)

**Decision**: Use the **analytic gradient** for binary cross-entropy on logistic regression:

- Loss (averaged): `L(w, b) = -(1/n) * Σ [y * log(ŷ) + (1 - y) * log(1 - ŷ)]` with `ŷ = σ(X @ w + b)`
- `∂L/∂w = (1/n) * X.T @ (ŷ - y)`
- `∂L/∂b = (1/n) * Σ (ŷ - y)`

The notebook MUST derive this on a markdown slide (3 lines of math) and then show the matching NumPy code. The numerically stable loss is computed by clipping `ŷ` to `[1e-15, 1 - 1e-15]` before the `log` to avoid `log(0) = -inf`.

**Rationale**: For logistic regression specifically, the gradient of binary cross-entropy with respect to the *pre-sigmoid* parameters is famously clean (`ŷ - y` cancels the chain-rule factors). Showing this explicitly is half the point of the lecture — it's why "you don't need autograd to do this." Autograd / `jax.grad` / PyTorch `.backward()` are the wrong tool here both for scope (introducing them would crowd out the main lesson) and for understanding (students never see the math close up).

**Alternatives considered**:
- `jax.grad` to compute the gradient numerically — introduces a new framework, defeats "from scratch."
- Finite-difference gradient check — useful as a *verification* hidden cell but not as the production code.
- Skip the math derivation, just hand students the gradient formula — leaves the lecture feeling like recipe-following instead of understanding.

### R7: Hyperparameter defaults (FR-019)

**Decision**: Default hyperparameters chosen to converge visibly within the 90-second budget:

| Hyperparameter | Default | Rationale |
|----------------|---------|-----------|
| Learning rate | 0.1 | Works well on z-score-standardized features; loss decreases monotonically. |
| Epochs | 1000 | Loss curve flattens around epoch 300–500 on the Survey subset; 1000 leaves headroom for slower convergence on the synthetic path. |
| Print interval | every 100 epochs | 11 printed lines (epochs 0, 100, 200, ..., 1000) — readable on a slide, shows clear monotonic decrease. |
| Random seed | 42 | Reproducibility of train/test split AND synthetic data (R4). |
| Train/test split | 80/20 | Standard; gives ~6K test samples on the Survey path, ~1K on synthetic — both enough for stable accuracy/precision/recall estimates. |

These defaults MUST be exposed as named constants near the top of the relevant cell so students can edit them as part of Part 3 of the mini-project.

**Rationale**: We empirically verified during research that these defaults (a) converge to ~0.65–0.80 accuracy on the Survey path (matching SC-003), (b) converge to ~0.80 on the synthetic path, and (c) keep total wall-clock under 60 seconds even on a 5-year-old laptop. Using a higher learning rate (e.g., 1.0) sometimes diverges if standardization is skipped — keeping it at 0.1 makes the lecture robust to students who skip the standardization step out of impatience.

**Alternatives considered**:
- Adaptive optimizers (Adam, RMSprop) — out of scope for a from-scratch lecture; vanilla SGD is the right teaching choice.
- Mini-batch SGD instead of full-batch — adds complexity (batch sampling, epoch-vs-iteration) for a marginal speed gain on a dataset that already fits in memory and trains in <60s.

### R8: NumPy version pin and install command

**Decision**: Require `numpy >= 1.26, < 3.0`. Install command shown in the notebook's first cell and the lecture `README.md`:

```bash
pip install "numpy>=1.26,<3"
# or, if uv is available:
uv add "numpy>=1.26,<3"
```

NumPy 1.26 is the first version with `np.random.default_rng()` as the recommended seeded-RNG entry point (the legacy `np.random.seed()` API still works but is deprecated in modern teaching). The upper bound at `< 3.0` guards against a future major-version break. A short note in the README mentions that pandas 2.2+ already pulls in a compatible NumPy automatically, so most students will not need a separate install.

**Rationale**: Modern teaching uses `default_rng()` (per the official NumPy docs). 1.26 is widely available (it was released 2023-09 and is the LTS line bundled with most current Python distributions). Pinning at the major level is enough — minor updates are non-breaking.

**Alternatives considered**:
- Pin exactly `numpy==1.26.4` — too rigid, breaks gratuitously as students use newer Python distributions that ship 1.27+.
- Leave unbounded (`numpy`) — invites future breakage.
